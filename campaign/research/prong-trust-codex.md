# Trust and authorization prong - independent Codex specification

Date: 2026-07-23

Status: design closed. Every proposed runtime node is `kind: build`, `tier: default`
(Opus under the campaign tier mapping). This prong adds no Fable planning or judging node.

## Executive decision

The relay is **outside the trusted set for PC control and terminal display integrity**.

A compromised relay or VPS must not be able to cause muxd or the desktop bridge to execute a
byte, resize, create, relaunch, kill, rename, heal, ACL change, file-fetch, transcript request, or
other PC-side action unless the executing PC endpoint verifies an authorization proof from an
allowed principal.

The relay remains intentionally able to read terminal input, terminal output, transcript pages,
fleet tails, archive indexes, and metadata. This campaign does **not** add end-to-end
confidentiality. That is an explicit product tradeoff, not an accidental omission. Network links
still use TLS, but a compromised relay host sees plaintext.

The trusted set is:

1. muxd, the desktop bridge, and their ACL-protected state on the PC.
2. The Windows account and local recovery path that administer muxd.
3. A trusted browser client build delivered from an origin that is administratively independent
   of the relay VPS.
4. Each provisioned client device's non-extractable private signing key.

The relay process, nginx on the relay VPS, the VPS filesystem, the relay database/state directory,
and the network between client, relay, and PC are not control authorities.

`hl-auth` owner authentication remains useful as an admission and privacy gate for an honest
relay. It is not evidence muxd accepts as authority to control the PC.

Confidence:

- High: the relay must be outside the control-authority set.
- High: authoritative write arbitration must move to muxd.
- High: lease tokens, intent IDs, and relay-issued assertions are not principal proof.
- Medium: P-256/WebCrypto is the lowest-dependency cross-browser implementation choice; the exact
  crypto wrapper should be proven by the cross-runtime vectors before broad implementation.
- Medium: the independent trusted-client deployment is operationally disruptive, but there is no
  sound way to keep a signing key in JavaScript delivered by the untrusted relay.

## Security properties

After enforcement is enabled:

1. Every PC-side mutation names a principal, resource, operation, expiry, and replay fence.
2. muxd or the desktop bridge verifies the proof at the execution boundary.
3. A relay-generated or relay-modified mutation is rejected.
4. A valid proof for session A cannot be replayed against session B.
5. A revoked principal or key cannot open a new channel or execute another mutation.
6. Lease takeover and lease expiry are decided from muxd state and muxd time.
7. Terminal output and authoritative control responses are signed by muxd. The trusted client
   refuses modified, reordered, replayed, or unsigned output.
8. The relay can withhold traffic and cause denial of service. Availability is not made
   Byzantine-fault tolerant.
9. The relay can read all plaintext. Relay-blind confidentiality is not claimed.

## Principal model

### Identifiers

- `instanceId`: random 128-bit ID generated once by muxd and stored durably.
- `principalId`: random 128-bit ID for one provisioned device or automation identity.
- `keyId`: base64url SHA-256 digest of the canonical public key bytes.
- `sessionUuid`: random 128-bit immutable mux session ID generated by muxd. It is distinct from
  the mutable mux name and from an agent transcript/resume ID.
- `channelId`: random 128-bit ID for one authenticated viewer attachment.
- `intentId`: random 128-bit ID for a durable or management operation.

All IDs use a strict base64url or lowercase-hex grammar with fixed maximum lengths. User-visible
labels are metadata and never authority.

### Keys

- Each browser device generates a P-256 ECDSA key pair with WebCrypto.
- The private key is `extractable:false` and stored only in IndexedDB under the trusted client
  origin.
- muxd stores the public key and authorization metadata. The relay does not need the registry.
- muxd has its own P-256 identity key. Its private half remains on the PC under an Ahmed/SYSTEM
  ACL. Clients receive the public key fingerprint during physical pairing.
- ECDSA signatures use SHA-256 and a pinned 64-byte `r || s` wire encoding.

The relay may observe public keys and signatures. It never receives client private keys, muxd's
private identity key, or a reusable authorization bearer that can originate input.

### Global scopes and session roles

Global principal scopes:

- `session.create`
- `archive.read`
- `archive.mutate`
- `upload.fetch`
- `principal.admin`

Per-session roles:

- `view`: may attach and request snapshots/history in the honest-relay model.
- `drive`: may type, paste, click, resize, acquire, and steal the write lease.
- `manage`: may kill, rename, change heal policy, and edit that session's ACL.
- `owner`: shorthand for `view + drive + manage + delegate`.

The `view` role does not protect confidentiality from a compromised relay because the relay sees
the plaintext stream. It is still useful for normal multi-user behavior. `drive` and `manage` are
enforced end to end at muxd and remain meaningful when the relay is compromised.

The session creator receives `owner`. Existing sessions do not silently grant remote drive during
migration. They must be claimed locally or assigned by an already provisioned `principal.admin`.

### Durable state

muxd owns:

- `muxd-identity.json`: instance ID and encrypted/ACL-protected identity private key.
- `principals.json`: public keys, labels, global scopes, creation time, key status, revocation
  epoch, and audit metadata.
- Per-session ACL and `aclRevision` in the session manifest.
- Per-session write lease and `leaseEpoch`; lease state itself is in memory, while epoch changes
  caused by revocation or management operations are persisted with the session.
- Durable intent results for management, durable-send, and deferred-send operations.

All files use the existing durable tmp/fsync/replace discipline. Private material is excluded from
relay backups.

## Provisioning, rotation, and revocation

### Initial pairing

1. A local recovery user runs:

   `muxctl pair create --label phone --scope session.create --session <name>:owner`

2. muxd creates a one-time 256-bit pairing secret, a pending grant record, and a five-minute
   expiry. The allowed scopes and ACL grant are fixed in the pending record; the browser cannot
   ask for more.
3. muxctl displays a QR code whose URL fragment contains `instanceId`, muxd's identity public-key
   fingerprint, `pairingId`, and the pairing secret. URL fragments are not sent to the static
   origin's server.
4. The trusted client generates its non-extractable P-256 key pair and sends a registration body
   through the relay. The body includes the public key, label, pairing ID, and a random nonce,
   plus `HMAC-SHA256(pairingSecret, bodyBytes)`.
5. muxd verifies the HMAC, exact pending grant, expiry, and single-use state, then creates the
   principal and ACL entries.
6. muxd returns an identity-signed receipt binding the principal, key, grants, and client nonce.
   The client verifies it against the identity fingerprint from the QR code before reporting
   success.
7. Both sides erase the pairing secret. Exact replay of the accepted registration is idempotent;
   any altered or second registration is rejected.

The relay can suppress pairing or replay the exact accepted request. It cannot register its own
key or enlarge the pending grant.

### Key rotation

A normal rotation carries:

- the new public key,
- a rotation intent signed by the old active key,
- proof of possession signed by the new key,
- an expiry and intent ID.

muxd activates the new key and returns a signed receipt. The old key remains active only for the
explicitly requested bounded grace period, then is revoked. The UI must not claim rotation
succeeded until it verifies muxd's receipt.

A lost or suspected-compromised sole key cannot rotate itself. Recovery requires either:

- a different active `principal.admin`, or
- the local muxctl recovery path on the PC.

### Revocation

- Principal revocation rejects all keys for that principal.
- Key revocation rejects only the named key.
- Session ACL revocation increments `aclRevision` and `leaseEpoch`, clears any lease held by the
  revoked channel/principal, and is checked again on every frame.
- Existing channels are invalidated immediately after the revocation commit.
- A remote revoke can be withheld by the relay, so the UI waits for a signed muxd receipt. Local
  revocation is the guaranteed recovery path.

## Signed authorization protocol

The campaign protocol number remains 4. This design adds capabilities and fields only:

- `principalAuthV1`
- `principalAclV1`
- `muxdSignedOutputV1`
- `muxdWriteLeaseV1`
- `deferredInputV1`

### Canonical signature transcript

Do not sign re-serialized arbitrary JSON objects. Every operation defines a fixed positional
array containing only bounded ASCII identifiers, integer timestamps/counters, and a SHA-256 body
digest:

```text
[
  "mux-authz-v1",
  op,
  instanceId,
  principalId,
  keyId,
  sessionUuid,
  channelId,
  seq,
  leaseEpoch,
  aclRevision,
  issuedAtMs,
  expiresAtMs,
  intentId,
  bodySha256
]
```

The signed bytes are UTF-8 `JSON.stringify(array)` with no whitespace. Python emits the same
bytes using compact separators. Cross-runtime golden vectors pin the byte string, digest, public
key, and accepted/rejected signatures.

The operation body is transported as exact `bodyB64` bytes. muxd hashes those bytes before parsing
the operation-specific schema. The relay cannot exploit alternate JSON serialization to change
the meaning after signature verification.

### Channel open

The trusted client sends a signed `channel.open` containing:

- session UUID,
- a fresh 256-bit `clientNonce`,
- requested role,
- current client time and a short expiry.

muxd verifies the principal and ACL, then returns an identity-signed `channel.accept` binding:

- the client nonce,
- a new channel ID,
- session UUID,
- current ACL revision,
- current lease epoch and holder,
- output stream epoch/checkpoint,
- channel expiry.

The client renders no authoritative terminal state and sends no input until this receipt verifies.

### Interactive input

Each raw input frame is signed and binds:

- `op = input.raw`,
- channel ID,
- session UUID,
- exact next sequence number,
- current ACL revision and lease epoch,
- capture time and expiry,
- SHA-256 of the raw input bytes.

Rules:

- Normal interactive expiry is 5 seconds; the hard protocol maximum is 15 seconds.
- muxd requires `seq == nextSeq`.
- An exact duplicate of an already accepted sequence returns the cached acknowledgement.
- Same sequence with a different digest closes the channel.
- A gap is rejected and requires retransmission/resynchronization.
- muxd checks `drive` authorization again before every write.
- Input is written only after signature, expiry, sequence, ACL, and lease checks pass.
- The relay never receives a reusable post-auth channel bearer that can create new frames.

The reconnect buffer holds captured plaintext only in the trusted client. Re-signing after a
reconnect preserves the original capture time and expiry; reconnect does not make stale input
fresh again.

### Durable and management intents

`input.durable`, create, relaunch, kill, rename, heal, ACL changes, key changes, file-fetch, and
desktop-bridge commands use `intentId`, expiry, operation-specific body bytes, and the same
principal signature format.

The execution endpoint persists `(principalId, keyId, intentId, bodySha256, outcome)` before and
after the side effect. Exact replay returns the cached result. Reuse with a different digest is
rejected. An uncertain prior outcome is never replayed automatically.

### Operation authorization

| Operation | Required authorization | Executing authority |
|---|---|---|
| `input.raw`, `input.durable`, paste, click, resize | session `drive` + current muxd lease | muxd |
| `lease.steal` | session `drive`, session policy allows steal | muxd |
| create | global `session.create` | muxd |
| relaunch, kill, rename, heal | session `manage` | muxd |
| ACL grant/revoke | session `owner` or global `principal.admin` | muxd |
| key rotate/revoke | principal self-rotation or `principal.admin` | muxd |
| transcript/archive read | global `archive.read`, current resource membership | desktop bridge |
| collection/title/archive mutation | global `archive.mutate` | desktop bridge |
| fetch uploaded file into PC/prompt | global `upload.fetch` | desktop bridge |
| start mux from archive | global `session.create`, current projection membership | desktop bridge, then muxd |

The desktop bridge verifies the same signature contract against the PC-side principal registry
before any side effect. `leaseToken`, `replayPolicy`, and `intentId` remain useful replay and work
distribution fields, but are not authorization.

## Authoritative multi-viewer write lease

The relay-side lease in `plan-design-revision.md` item 3 is replaced as an authority.

muxd owns per-session:

```text
holderPrincipalId
holderKeyId
holderChannelId
lastAcceptedInputMonotonic
leaseEpoch
```

Policy:

1. A signed input from the holder refreshes the lease.
2. If no holder exists or the holder has been idle longer than
   `MUX_INPUT_LEASE_MS` (default 3000 ms), a signed input may atomically acquire the lease.
3. Acquisition increments `leaseEpoch`; the accepted input and acknowledgement bind the new
   epoch.
4. Input from a different channel while the lease is fresh is rejected before the PTY write with
   a signed `lease-held` response.
5. A signed `lease.steal` from any authorized `drive` principal transfers immediately and
   increments the epoch.
6. Frames carrying an old epoch are rejected. This prevents delayed bytes from the previous
   holder landing after a takeover.
7. Revocation, ACL removal, channel close, session restart, and explicit release clear the holder
   and increment the epoch where needed.

The relay may keep an advisory cache solely to render the banner quickly. Clients treat only
muxd-signed lease state as authoritative. A compromised relay can lie about the banner, steal
button result, or availability, but it cannot make muxd accept input from the wrong holder.

There are no relay-originated writes:

- `/send` forwards an already signed client intent.
- Quick replies are signed by the client at tap time.
- "Send when idle" is a signed delegation stored and evaluated by muxd.
- A relay notification or timer cannot mint input or steal a lease.

### Send when idle

The client signs the exact text plus:

- session UUID,
- condition (`working -> idle|attention`),
- earliest execution time,
- expiry, maximum 24 hours,
- `maxExecutions = 1`,
- intent ID.

muxd persists the delegation, evaluates the condition from its local session state, acquires or
steals the lease according to the signed delegation, executes once, and records the result.
Cancellation is another signed intent. The relay stores only a display mirror and can suppress
delivery/status, but cannot trigger early, change text, extend expiry, or execute twice.

## Signed terminal output and control state

Leaving output unauthenticated would let a compromised relay draw a fake prompt and manipulate the
human into signing harmful input. Therefore plaintext is allowed, but silent tampering is not.

muxd signs every coalesced output frame and authoritative control response using its identity key.
The signed transcript binds:

```text
[
  "mux-output-v1",
  instanceId,
  sessionUuid,
  streamEpoch,
  outSeq,
  previousFrameHash,
  frameType,
  requestNonce,
  payloadSha256
]
```

Requirements:

- Output sequence and hash chain are per session and stream epoch.
- Attach, replay, snapshot, digest, resync, lease state, ACL receipts, and mutation outcomes are
  signed.
- `channel.accept` binds the client nonce to the current output checkpoint, preventing an old
  attach transcript from being replayed as current.
- The trusted client verifies before writing bytes to xterm or applying a snapshot.
- A missing sequence marks the viewer desynced. Recovery requires a signed snapshot/replay bound
  to the request nonce.
- Relay-side backpressure may drop frames, but cannot create a valid replacement.
- The relay can still read, store, index, and fan out the plaintext.

## Confidentiality decision

End-to-end encryption is **not warranted in this campaign** because the current product explicitly
uses relay-visible data for:

- live terminal fan-out,
- fleet snippets,
- transcript page storage and reading,
- history/search surfaces,
- notifications containing session context,
- relay-side archives and retention.

Encrypting only one path would create a misleading partial guarantee. A real relay-blind design
would require:

1. Per-session content-encryption keys and epoch rotation.
2. Key wrapping to every authorized viewer.
3. Ciphertext-only relay storage.
4. Full-text search moved to muxd or the client.
5. Fleet snippets and content-bearing notifications removed or produced by the PC.
6. Client-side transcript decryption and indexing.
7. Forward-only revocation semantics because already viewed plaintext cannot be recalled.

That is a coherent future architecture, but it is a separate product decision. For this campaign:

- TLS protects traffic from ordinary network observers.
- The relay VPS sees input, output, archives, transcripts, and metadata.
- muxd signatures protect integrity, not secrecy.
- UI and documentation must not claim the relay is blind or zero-knowledge.

## Residual power of a compromised relay

A compromised relay can still:

1. Deny service by dropping, delaying, reordering, or terminating connections.
2. Withhold pairing, grants, revocations, lease notices, acknowledgements, and signed output.
3. Read every plaintext keystroke, terminal byte, transcript page, archive row, search term, fleet
   snippet, session name, timing signal, IP address, and device label that passes through it.
4. Replay signed frames. muxd rejects duplicates, stale epochs, expired intents, and sequence
   reuse, but replay attempts still consume bounded verification work.
5. Lie in relay-local UI, notifications, unsigned metadata, archive ordering, and availability.
6. Selectively starve one principal or session.
7. Manipulate its advisory lease cache and banner.
8. Request read-side work and consume bounded resources; read operations need quotas even when
   confidentiality from the relay is not a goal.
9. Corrupt or delete relay-resident transcript/archive state.

It cannot, without a valid authorized-principal proof:

- inject terminal input,
- resize a PTY,
- create/relaunch/kill/rename/heal a mux session,
- steal the muxd write lease,
- edit a muxd ACL or principal registry,
- execute a desktop-bridge command,
- forge muxd output or a muxd success receipt accepted by the trusted client.

The relay can still socially manipulate the user through relay-local content. Signed terminal
output limits that attack for live shell state, but not for all relay-originated prose or
notifications.

## Transport and local-bypass obligations

End-to-end authorization does not excuse weaker adjacent boundaries.

1. muxd's local websocket must no longer be "loopback-only, no token." Every local connection
   authenticates in its first frame using a separate high-entropy local-control credential.
2. `muxd.env`, the local-control credential, muxd identity private key, and principal state receive
   explicit Ahmed/SYSTEM ACLs with inherited sandbox-group access removed.
3. Local muxctl is the recovery principal. It may manage ACLs and sessions after authenticating
   locally, but its credential is never accepted on the relay host link.
4. The muxd-to-relay link uses `wss://` with normal certificate validation or an explicit pin.
5. The host token moves from the URL query to an `Authorization` header, is scoped only to the
   host link, and is rotated after ACL hardening.
6. The Node relay binds loopback. nginx terminates public TLS and proxies both browser and `/host`
   traffic. Direct public port 7682 is closed.
7. Bridge push/poll routes use a distinct scoped bridge credential. Ambient loopback is removed.
8. Authentication and frame-size/rate checks happen before expensive signature verification.

These controls reduce LAN, local-sandbox, log, and resource-exhaustion risk. They do not make the
relay a PC-control authority.

## Trusted client deployment

The signing client cannot be JavaScript fetched from the relay VPS. If the relay can replace the
code that calls `crypto.subtle.sign`, it can use the device key to authorize arbitrary input.

Decision:

- Keep the web client source in this repository so existing UI leaves can continue to edit it.
- Publish a versioned build to `MUX_TRUSTED_CLIENT_ORIGIN`, hosted outside the relay VPS and under
  a separate deployment credential.
- The private key is stored only under that origin.
- The relay-served copy is read-only after `principalAuthV1` enforcement and redirects driving
  users to the trusted origin.
- The trusted build has a pinned API/WS base, strict CSP, no third-party scripts, no dynamic code,
  and `frame-ancestors 'none'`.
- The relay allowlists that Origin for browser WebSocket upgrades.
- The UI shows the muxd identity fingerprint, principal label, session UUID suffix, ACL role, and
  verified lease state in a trusted status strip.

Operational break:

- Existing browser localStorage/IndexedDB under the relay origin does not migrate the private key.
- Each device must pair again under the trusted origin.
- Clearing browser storage loses the key and requires re-pairing.
- Old clients become read-only when enforcement flips.
- Offline raw-input fallback is removed; no unsigned path remains.

## Rejected alternatives

### Put the relay inside the trusted set

Rejected. Hardening a rented VPS is necessary, but it only reduces compromise probability. It
does not reduce the consequence from "relay compromised" to anything less than "developer shell
compromised." The campaign should not equate operational care with an authorization proof.

### Let the relay sign JWTs or MACs for muxd

Rejected. A key held by the relay lets a compromised relay mint any principal, session, lease, or
input claim. It restates the problem in a different encoding.

### Treat lease token plus intent ID as authentication

Rejected. They prove freshness, deduplication, and work ownership. The relay legitimately creates
or forwards them, so they do not prove who authorized the operation.

### Keep the principal key in the current relay-served page

Rejected. A compromised relay can serve altered JavaScript that invokes the key. A non-extractable
key prevents export, not unauthorized use by code running in its origin.

### Use WebAuthn confirmation for every input frame

Rejected. It is unusable for continuous terminal input and browser authenticators do not present
the signed terminal bytes as a trustworthy transaction display.

### Keep authoritative arbitration at the relay

Rejected. An untrusted relay can forge holder state, steal, reorder, or selectively apply the
lease. muxd already owns the resource and must own the lease decision.

### Preserve a raw unsigned input fallback

Rejected. Attackers choose the weakest accepted path. A fallback that bypasses principal proof
nullifies the model.

### Add full end-to-end encryption now

Rejected for this campaign because it disables or relocates major planned value features. The
tradeoff is recorded above so a future confidentiality project starts from an honest boundary.

### Rely on remote revocation through the relay

Rejected. The relay can suppress it. Remote revocation is convenient only after a signed muxd
receipt; local recovery remains mandatory.

### Bump protocol 4

Rejected. The current relay requires exact protocol equality. All changes are additive
capabilities/fields with staged enforcement.

## Honesty mechanism

The mandatory negative test is:

1. Create a muxd session with an ACL granting principal A `drive`.
2. Feed muxd a syntactically valid host-link `input.raw` frame with a valid session, sequence,
   lease epoch, body, intent ID, and dimensions, but **no authorized-principal signature**.
3. Assert muxd returns `principal-proof-required`.
4. Assert the fake PTY write count remains zero.
5. Assert lease holder, lease epoch, input journal, and session state remain unchanged.

The same suite also covers bad signature, unregistered key, revoked key, wrong session UUID,
expired frame, stale ACL revision, stale lease epoch, duplicate sequence, and valid proof exactly
once.

This test belongs to the muxd enforcement leaf and is repeated through the real three-process
trust smoke. A test that only exercises relay rejection is insufficient; the executing endpoint
must prove the rejection.

## Existing plan leaves that become wrong or insufficient

### Replace

1. **r.1 child 18, `Plan node: decompose the MUX_SYSTEM_AUDIT security fix-order`.**
   Replace it with trust-1 through trust-12. Its Fable planning shape will refuse at runtime, and
   the design is now closed.
2. **Design revision r.3 child 16, relay input write lease.**
   Replace the authority with trust-5. The relay may keep only a signed-state UI mirror.
3. **r.2 child 13, relay-owned send-when-idle.**
   Replace its queue/execution authority with trust-7. A relay-generated intent ID is not
   authorization.

### Amend materially

1. **r.2 child 3, muxd durable input-intent host frame.**
   `intentId` alone is insufficient. The host frame must carry the trust-auth-v1 envelope and muxd
   must reject proofless input.
2. **r.2 child 9, relay `/send`.**
   It may validate transport bounds and correlate results, but must forward an existing signed
   envelope byte-for-byte and never mint the body or authority fields.
3. **r.2 child 12, composer durable send.**
   Remove the raw unsigned fallback. Composer, paste, and enter all use the trusted signer.
4. **r.2 child 14, quick replies.**
   Each tap produces a fresh signed durable input or interactive frame.
5. **r.3 child 8, reconnect input continuity.**
   The buffer belongs to the trusted client origin. Reconnect preserves original capture time and
   expiry; the relay does not store or re-sign plaintext.
6. **r.3 child 6, click forwarding.**
   Passed clicks are signed `input.raw`; no direct `send('i', ...)` bypass remains.
7. **r.3 child 5, latency probe.**
   Measure the enforced signed path as a separate series so crypto cost is visible.
8. **r.1 child 10, lease+intent envelope for app commands.**
   Lease and intent checks remain, but trust-11 adds actual principal proof. The existing leaf is
   not an authorization fix by itself.
9. **r.1 child 11, ws frame validation.**
   Keep it as parser hardening, but do not describe it as defense against a compromised relay.
   Authenticated endpoint verification is the boundary.
10. **r.1 child 1, protocol registry.**
    Add all trust-auth-v1 frames, caps, error codes, signed response shapes, and the protocol-4
    additive rule.
11. **Design revision r.3 child 17, viewer backpressure.**
    Resync payloads and gap recovery must preserve muxd signatures; the client resumes only after
    a signed nonce-bound snapshot/replay.
12. **Design revision r.3 child 18, divergence detector.**
    Digest and corrective snapshot must be muxd-signed. A relay-provided digest is not authority.
13. **r.3 children 12-15, model snapshot/sbtext/history.**
    muxd signs snapshot, sbtext, and digest responses; the trusted-origin client verifies before
    display. The relay continues seeing plaintext.
14. **r.2 children 4-7 and 15-16, archive/transcript surfaces.**
    Bridge pushes and lease/ack use the scoped bridge credential from trust-10. Any PC-side action
    triggered from archive/reader UI carries trust-11 principal proof. Plaintext relay storage and
    disclosure remain accepted.
15. **r.2 child 5 and r.2 child 7 loopback-only POSTs.**
    Ambient loopback is removed. These become bridge-credential routes.
16. **r.2 child 10 fleet tails.**
    Tail responses shown as terminal truth must be muxd-signed and verified by the trusted client.
17. **Plan-design-revision r.2 child 20, three-process smoke.**
    Fold its functional coverage into trust-12 or make it a prerequisite. The old unsigned
    keystroke success case is no longer sufficient.
18. **r.1 child 19 and r.2 child 17 test gates.**
    Add trust tests automatically through their directory globs and make trust-12 a semantic
    prerequisite before the relay gate is considered final.
19. **Root final campaign judge.**
    It may rerun fixed trust verifiers and report results, but must not reopen this design or emit a
    new deep trust-planning child.

## Integration order

Recommended order:

```text
trust-1
  -> trust-2
       -> trust-3
       -> trust-4 -> trust-5 -> trust-6 -> trust-7
       -> trust-9 -----------------------> trust-10 -> trust-11
       -> trust-8
all trust-4..11 -> trust-12
```

Practical rollout:

1. Land contract vectors and durable principal state.
2. Land trusted client pairing/signing while muxd remains in audit mode.
3. Land muxd verification and authoritative lease.
4. Convert every browser/relay/app mutation path; remove raw fallbacks.
5. Sign and verify output.
6. Authenticate local control, harden ACLs, deploy scoped WSS transport, and rotate credentials.
7. Pair devices and claim existing sessions.
8. Run trust-12 positive and negative cases.
9. Flip enforcement to default.

The enforcement flip is last. Shipping endpoint enforcement before a trusted client and recovery
principal exist would lock out legitimate control; shipping the trusted client while muxd still
accepts raw input would preserve the vulnerability.
