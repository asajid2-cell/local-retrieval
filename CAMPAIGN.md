# Campaign: Multiplex Reliability Parity

## Win Condition (change-controlled)
- `multiplex` in a local Windows terminal and `https://harmonizerlabs.cc/multiplex/` address the same PC-hosted muxd sessions.
- Starting a session locally makes it appear on the web; starting a session on the web makes it attachable locally.
- A named active session can be attached locally without creating a VPS tmux twin.
- After reboot, unarmed sessions do not auto-run agents. Only explicitly armed watcher/autoheal sessions may auto-start.
- Web responsiveness is attributable with logs/probes; no unexplained fallback, twin creation, or empty-state disagreement remains.
- Latency-parity target: starting/attaching through multiplex should be attributable against local-terminal baselines. Any remaining overhead must be named as startup shell/ConPTY, transport, browser rendering, or launcher compatibility.
- HUMAN-GATE: the user confirms the site feels responsive enough during real agent work.

## Constraints & Anti-goals
- Do not kill live agent sessions unless a verifier requires it and there is no non-disruptive path.
- Do not restore the legacy default where every reboot or plain tab visit auto-starts all saved agents.
- Do not let VPS tmux be the normal ownership model; muxd on this PC owns the real terminals.
- Preserve existing unrelated repo changes.

## Learnings
- The word "session" currently names several things: old VPS tmux, PC-local muxd headless PTY, visible local `muxrun` owner, and relay-visible mirror. Reliability requires one normal ownership path: PC-local muxd headless first; web and local terminal are both attach clients.
- Windows Defender Controlled Folder Access is enabled, and direct writes to `C:\Users\Ahmed\Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1` are denied from this process. Do not spend more campaign time restoring the `multiplex` function: it is deprecated, `mux` is canonical, and the VPS helper it invokes fails closed.
- `muxctl attach/open` is again the local attach path for the canonical PC-local muxd session. The user-facing local command is `mux`, which opens/attaches a muxd PTY; it is not a VPS tmux bridge.
- Cold-start cost for app/web start is PC-local ConPTY + shell/agent startup. Runtime work survives VPS/relay loss because muxd and the child process live on the PC.
- Remote/web is an attach client to muxd, not an owner. Bounded scrollback and short sb wait remain important because browser rendering can still feel laggy even when the PC PTY is healthy.
- A TCP listener on `127.0.0.1:7699` is not enough evidence of muxd health. Use `muxctl status` loop-lag/local-control counters and `muxd.log.stacks` if another stall appears.
- A running local agent process and a muxd-hosted terminal are not the same state. The relay must not collapse "local PID still alive but muxd mirror detached" into "dormant/no agent running"; that was the misleading state Ahmed saw.
- Synchronous ConPTY/winpty calls must not run on muxd's asyncio loop. The loop is the fan-out point for every browser terminal, status push, and input path; a single blocking `isalive()`, spawn, resize, or terminate call can freeze all web terminals and then flood output when it recovers.
- "Alive" is not a sufficient session state. Relay/app decisions need to know whether a hosted PTY is shell-only, command-backed, or dormant, and command-backed rows need a stable signature so a resume/start request cannot be acknowledged by the wrong live terminal.
- Relay optimistic rows are UI hints, not proof. API success that claims a session started must wait for muxd to report the session back with compatible command state; otherwise the website can show a tab as started while muxd never actually accepted it.
