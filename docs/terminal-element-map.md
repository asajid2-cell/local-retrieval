# Terminal element map - OSC 21338

Status: source of truth for the gateway repo. The fixture next to this file is
generated by `scripts/element-map-vectors.ts` from `src/ink/element-map.ts` and
is checked byte-for-byte by `scripts/element-map-vectors.test.ts`. If the two
disagree, the codec changed and the contract changed with it; regenerate and
review the diff.

Scope: how the renderer puts a semantic map of the frame it just wrote onto the
VT stream, and the exact rules a consumer's stripper must follow to separate
that map from text and from every other escape sequence. The consumer owns
nothing in this stream except the right to read it.

## Wire format

An emitted sequence is exactly:

```
ESC ] 2 1 3 3 8 ; <base64url of UTF-8 JSON> ESC \
1b 5d 32 31 33 33 38 3b   ...                     1b 5c
```

A relayed stream may carry the 8-bit form `9d 32 31 33 33 38 3b ... 9c`.

The payload is a JSON object:

```json
{"v":1,"gen":3,"cols":80,"rows":24,"els":[
  {"id":"e1","role":"text","r":[2,3,24,1],"label":"Build passed","act":{"t":"ptr","x":14,"y":3,"b":0}}
]}
```

- `v` is `1`. A consumer that does not know the version drops the frame.
- `gen` advances only when the map changes; a heartbeat re-sends the same `gen`.
  `0` means nothing has ever been sent.
- `cols`/`rows` are the frame geometry the rects were computed against.
- `els` is the full list every frame - never a delta. Duplicate ids resolve
  last-wins.
- `r` is `[x, y, width, height]` in app-space cells, 0-based. An element may be
  outside the viewport (scrolled out) but is not emitted if it did not paint.
  For a text element this is the **laid-out node's rect, not the glyph bounding
  box**: a title text laid out across the row reports `[0,0,80,1]` even though
  its glyphs occupy five cells, and a four-character label inside a 12-wide box
  reports its own text node (four cells), not the box. Do not derive hit
  boundaries from label length.
- `id` is assigned the first time a node paints and is stable for that node's
  lifetime. A node skipped on an early frame gets its id later, so a parent can
  carry a higher id than a child; `els` order is paint order and id identity is
  a separate guarantee. Consumers key overlays on `id`, not on position in the
  array.
- `label` is present only where the node renders text; 120 characters max,
  collapsed to one line, ending in `…` when cut.
- `act` is one of:
  - `{"t":"ptr","x":C,"y":R,"b":0|1|2}` - synthetic pointer press at app-space
    cell `(x,y)`, button `b`.
  - `{"t":"key","d":"<base64url>"}` - bytes to replay verbatim. The consumer
    never parses them; `decodeKeyAction` is the only decoder.
  - `{"t":"focus"}` - text-entry target: focus the consumer's own widget.
  - `{"t":"none"}` - explicitly display-only.
  - absent - display-only (same effect as `none`; both arms exist in the
    schema and a validator must accept both).
- `role` is free-form; consumers must tolerate roles they do not know. The
  emitter publishes `box`, `text`, `link`, `progress` and `raw`.

## Introducers

**1. Legal introducers are exactly `ESC]21338;` and `0x9D 21338 ;`.** Anything
else is not ours and is passed through byte-for-byte.

**2. `ESC]21338` with no `;` is not an introducer, and neither is a
zero-padded command (`ESC]0021338;`).** Both pass through our stripper
unchanged. This is safe: any VT that does parse them treats them as an OSC of
command 21338 and prints nothing, so the only cost is that our stripper does
not count them as frames. No emitter in this tree produces either form (the
codec's introducer is a constant).

**2a. A stream that begins in the middle of a body is not ours.** With no
introducer in its input there is nothing to strip, so the fragment - and the
terminator that closes the orphaned body - pass through as text and `dropped`
does not move. A ring or replay source that evicts whole chunks can hand a
stripper exactly this. The fix belongs at the source (strip before the bytes
reach the ring); the stripper cannot invent an introducer that was never in its
input.

**3. Strip by command number, regardless of body validity.** A sequence that
starts with a legal introducer and ends at a terminator is consumed whole -
valid base64url that decodes to a conforming frame becomes a frame; anything
else is discarded and counted. This is safe because the body alphabet excludes
every terminator, so the sequence boundary cannot be spoofed from inside the
payload; and for a command we own, dropping an unrecognized body is the
correct action, not printing it.

**4. base64url is the law.** A body is `[A-Za-z0-9_-]+` with at most two
trailing `=` padding characters tolerated on input (this emitter never writes
padding). Anything else is rejected before decoding. No body byte can
therefore be ESC (`0x1b`), BEL (`0x07`), `0x9C`, CAN (`0x18`) or SUB (`0x1a`).
If a future payload needs an escape byte, a payload escaping rule must be
specified before emission changes.

**4a. A trailing partial introducer is held, in both forms.** A chunk that
ends in a suffix that could still become `ESC]21338;` **or** `0x9D 21338 ;` is
not printed; it is carried and prepended to the next chunk. This is a chunk
boundary, not a legal sequence: holding the ESC form only would print the
fragment and then print the next chunk's base64 as text, which is the exact
failure the stripper exists to prevent.

## Terminators and aborts

- BEL (`0x07`), `ESC\` (`1b 5c`) and `0x9C` end the string. The terminator is
  consumed and never appears in the text.
- ESC followed by anything other than `\` aborts the string **without
  consuming the ESC**: the ESC is the start of the next real sequence, so it
  survives into the text stream.
- CAN (`0x18`) and SUB (`0x1A`) abort the string and **are consumed** by the
  stripper; they do not appear in the output text.
- **An abort does not by itself discard a body that decodes.** The body before
  the abort is processed exactly like a terminated body: if it is valid
  base64url of a conforming frame the frame is delivered (`dropped` stays
  put); if it does not decode it is discarded and `dropped` increments. The
  rule "the aborted payload must not survive" therefore applies only to
  payloads that do not decode. A consumer must not assume an abort suppresses
  a well-formed body.
- The emitter only ever writes ST.

## Dropping

`dropped` increments once per abandoned sequence: an undecodable body (not
base64url, not JSON, wrong `v`, malformed element/action) including one cut
short by an abort, or a carry that exceeds `ELEMENT_MAP_MAX_CARRY_BYTES`
(64 KB).

On carry overflow the open sequence is abandoned and scanning resumes **inside
that same chunk** at the next legal introducer, so a valid frame behind the
garbage is not lost with it. The bytes between the overflow point and that
introducer are machine data: they are discarded, never printed. If the chunk
carries no further introducer its remainder is discarded, except for a trailing
partial introducer, which is held (rule 4a).

An abort (ESC, CAN, SUB) is not the same path: an ESC is not a terminator here,
so a frame that follows an unterminated body in one chunk is reached by the
abort route before the cap is ever consulted, and the frame is delivered.

An overflow cannot happen on a legal frame: 32 KB of JSON base64-encodes to
about 43.7 KB, well under the 64 KB carry cap. The cap only bites on corruption
or a truncated ring replay.

## Size

`ELEMENT_MAP_MAX_PAYLOAD_BYTES` is 32768 bytes of JSON, **inclusive**: a frame
measuring exactly 32768 bytes is accepted; 32769 is refused with
`{ok:false, reason:'too-large', bytes}`. A refused frame writes nothing at all
(the sequence is never truncated, because a half-written sequence prints
base64 to the screen). The previous map stays in place.

## Emission rules (publisher)

- `gen` advances only after a frame was actually written, and only when the map
  changed (elements or geometry). An unchanged re-render writes nothing.
- A resize with identical elements is a change: dedupe is on `gen` alone, not
  on the element list.
- A refused oversize frame leaves the previous map on the wire, returns
  `refused`, and does not advance `gen`.
- The heartbeat is periodic: once armed it is left alone. Publishing does not
  restart its countdown. It re-sends the last sequence byte-for-byte with the
  same `gen` every 10 s while the last map is non-empty.
- The empty map is emitted and cancels the heartbeat: it is the consumer's
  instruction to paint no widgets, and does not need refreshing.
- After `stop()` the publisher emits nothing, including from a previously
  armed heartbeat.

## One write per sequence

A sequence is handed to a single `write()`. Nothing writes a sequence in pieces
or interleaves another write inside it. A process killed inside that write
leaves the terminal inside an OSC string; one call bounds the exposure.

## OSC command namespace relied on

| command | owner | meaning |
| --- | --- | --- |
| 0, 1, 2 | xterm | window/icon title |
| 8 | xterm | hyperlinks |
| 52 | xterm | clipboard |
| 133 | shell integration | prompt marks |
| 1337 | iTerm2 | proprietary (inline images, files) |
| 21337 | this tree | tab status |
| 21338 | this tree | element map |

The stripper keys on `21338` alone. Every other command's sequences survive
untouched, including their ESC, BEL and ST bytes.

## Why base64url + ST

Raw JSON can contain `;` and a raw `0x9C` inside a string, which would split or
terminate the OSC early. base64url's alphabet contains nothing that can end the
sequence, so a body is opaque as far as the parser is concerned. ST rather than
BEL: BEL is a bell on every terminal that does not recognise the command, and
an unrecognised terminal should discard the map silently.
